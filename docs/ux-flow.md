## ២. ដំណើរទី ១ — ភ្ញៀវរុករក Tour (F1 · F2 · F4)

### ២.១ អេក្រង់ទំព័រដើម

```
GET /api/v1/tours/popular
GET /api/v1/categories
```

អេក្រង់បង្ហាញ `TourCardResponse` — សំខាន់ត្រង់ **field ដែលធ្វើឲ្យអ្នកប្រើចុច**៖

| Field | តួនាទីលើ UX |
|---|---|
| `thumbnailUrl` | រូបដំបូងដែលទាក់ភ្នែក |
| `price` + `durationDays` | អ្នកប្រើសម្រេចចិត្តភ្លាមថាតម្លៃសមឬអត់ |
| `averageRating` · `reviewCount` | ទំនុកចិត្ត — បើ `reviewCount = 0` កុំបង្ហាញផ្កាយទទេ ចូរបង្ហាញ "ថ្មី" ជំនួស |
| `nextDepartureDate` | **សំខាន់បំផុត** — បើ null មានន័យថា **គ្មានកាលវិភាគបើក** → ត្រូវបង្ហាញស្លាក "ឆាប់ៗនេះ" និង**លាក់ប៊ូតុងកក់** |

> ⚠️ **អន្ទាក់ UX**: `findPopular` ត្រងយក Tour ដែល `reviewCount >= 3` តែប៉ុណ្ណោះ។ ពេលប្រព័ន្ធថ្មី គ្មាន Tour ណាមានវាយតម្លៃ ៣ ទេ → **ទំព័រដើមទទេស្អាត**។ ត្រូវរៀបចំ fallback៖ បើបញ្ជីទទេ សូមបង្ហាញ Tour ថ្មីបំផុតជំនួស។

### ២.២ អេក្រង់ត្រង (Filter)

```
GET /api/v1/tours?keyword=&categorySlug=&minPrice=&maxPrice=
                 &minDays=&maxDays=&difficulty=&departureAfter=&sortBy=price_asc
```

`TourFilter` មាន ១០ ប៉ារ៉ាម៉ែត្រ។ ការរៀបចំ UX ល្អ៖

```
[ប្រអប់ស្វែងរក keyword                    ]

ប្រភេទ:     ( ) ទាំងអស់  ( ) ធម្មជាតិ  ( ) វប្បធម៌  ( ) សមុទ្រ
តម្លៃ:      [──●────────●──]  $50 – $300
រយៈពេល:    [1-2ថ្ងៃ] [3-5ថ្ងៃ] [6ថ្ងៃ+]
កម្រិតលំបាក: [ងាយ] [មធ្យម] [លំបាក]
ចេញដំណើរ:   [📅 ក្រោយថ្ងៃ...]

តម្រៀប:  ▼ តម្លៃទាប→ខ្ពស់
```

**ការណែនាំ**៖ ដាក់ `departureAfter = ថ្ងៃនេះ` ជាតម្លៃលំនាំដើម ដើម្បីកុំឲ្យអ្នកប្រើឃើញ Tour ដែលចេញដំណើររួចហើយ។

### ២.៣ អេក្រង់លម្អិត Tour

```
GET /api/v1/tours/{id}   -> TourDetailResponse
```

នេះជា **អេក្រង់សម្រេចចិត្ត** — `TourDetailResponse` ផ្ទុកអ្វីៗគ្រប់យ៉ាងក្នុង **request តែមួយ** ដើម្បីកុំឲ្យទំព័ររង់ចាំច្រើនដង៖

```
┌─ Gallery (images រៀងតាម sortOrder) ─┐
│  [រូប ១] [រូប ២] [រូប ៣] ...         │
└──────────────────────────────────────┘
   ចំណងជើង · ⭐4.5 (១២ វាយតម្លៃ) · $180
   ⏱ ៣ថ្ងៃ ២យប់ · 🥾 មធ្យម · 👥 ៤–២០ នាក់

   [description] [itinerary] [included] [excluded]   ← ថេប

   🗺 ទីតាំង: destinations[]

   📅 កាលវិភាគចេញដំណើរ  (upcomingSchedules[])
   ┌─────────────────────────────────────────┐
   │ ១២ តុលា → ១៤ តុលា   សល់ ៨ កៅអី  [កក់]  │
   │ ១៩ តុលា → ២១ តុលា   សល់ ២ កៅអី  [កក់]  │  ← ពណ៌ក្រហម
   │ ២៦ តុលា → ២៨ តុលា   ពេញ        [ ✕ ]   │  ← បិទ
   └─────────────────────────────────────────┘

   💬 វាយតម្លៃថ្មីៗ (recentReviews[] — ៥ ចុងក្រោយ)  [មើលទាំងអស់ →]
```

**របៀបបង្ហាញកាលវិភាគតាម `status`**៖

| `status` | UX |
|---|---|
| `OPEN` | ប៊ូតុង **[កក់]** ពណ៌ចម្បង + បង្ហាញ `availableSeats` |
| `FULL` | ប៊ូតុងប្រផេះ "ពេញហើយ" + តំណ "ជូនដំណឹងពេលមានកៅអី" |
| `CLOSED` | មិនបង្ហាញក្នុងបញ្ជីទាល់តែសោះ |
| `DEPARTED` / `COMPLETED` | មិនបង្ហាញ |
| `CANCELLED` | មិនបង្ហាញ |

> 💡 ពេល `availableSeats <= 3` សូមបន្ថែមអក្សរក្រហម **"សល់តែ ២ កៅអីទៀត!"** — ជំរុញការសម្រេចចិត្ត។

## ៣. ដំណើរទី ២ — ចុះឈ្មោះ (F6)

```
POST /api/v1/customers/register   -> RegisterCustomerRequest
```

### ៣.១ ជំហាន UX

```
១. អ្នកប្រើចុច [កក់] ខណៈមិនទាន់ login
       ↓
២. បង្ហាញប្រអប់ "ត្រូវមានគណនីសិន"  [ចូល] [ចុះឈ្មោះ]
       ↓  ← ត្រូវចាំ scheduleId ដែលគាត់ចង់កក់
៣. ទម្រង់ចុះឈ្មោះ
       ↓
៤. ចុះឈ្មោះជោគជ័យ → status = ACTIVE
       ↓
៥. ត្រឡប់មកអេក្រង់កក់វិញ ដោយស្វ័យប្រវត្តិ (កុំបោះទៅទំព័រដើម!)
```

### ៣.២ Validation ដែលអ្នកប្រើនឹងជួប

| Field | ច្បាប់ | សារកំហុសដែលត្រូវបង្ហាញ |
|---|---|---|
| `username` | ៤–៦០ តួ · `^[a-zA-Z0-9._-]+$` | ត្រូវពិនិត្យ **ភ្លាមៗពេលវាយ** (debounce ៥០០ms) ហៅ `existsByUsername` |
| `email` | `@Email` · មិនស្ទួន | ដដែល |
| `phoneNumber` | `^0[1-9][0-9]{7,8}$` | "លេខទូរស័ព្ទត្រូវចាប់ផ្តើមដោយ 0 និងមាន ៩–១០ ខ្ទង់" |
| `dateOfBirth` | `@Past` | ប្រើ date-picker ដែលបិទថ្ងៃអនាគត |

> ⚠️ **ចន្លោះប្រហោងក្នុងផែនការ**: `Customer` entity **គ្មាន field `password`** ហើយ `RegisterCustomerRequest` ក៏គ្មានដែរ។ មានន័យថាការ authenticate ត្រូវធ្វើតាមប្រព័ន្ធខាងក្រៅ (Keycloak) ដែល `username` ជាតំណភ្ជាប់។ **ត្រូវសម្រេចរឿងនេះមុនសរសេរ F6** ព្រោះវាប៉ះពាល់ដល់អេក្រង់ login ទាំងមូល។

> Feature ស្មុគស្មាញបំផុត។ សូមអានវិន័យ BR1–BR10 ក្នុង `pseudo-code.md` §F7.3 ជាមុន។

### ៤.១ អេក្រង់ ៣ ជំហាន

```
ជំហាន ១/៣ ─ ជ្រើសចំនួន           ជំហាន ២/៣ ─ អ្នកដំណើរ        ជំហាន ៣/៣ ─ បញ្ជាក់

│ កាលវិភាគ: ១២ តុលា  │         │ អ្នកដំណើរ ១ (មេ) ★ │      │ សង្ខេបតម្លៃ       │
│ សល់: ៨ កៅអី        │         │  ឈ្មោះ · ភេទ · ថ្ងៃកំណើត│      │ $180 × 5 = $900  │

│                    │         │  ...               │      │                  │
│ 💰 បញ្ចុះ ១០%!     │         │ អ្នកដំណើរ ៣ ៤ ៥    │      │ [បញ្ជាក់ការកក់] │
└────────────────────┘         └────────────────────┘      └──────────────────┘
```

### ៤.២ តារាងបញ្ចុះតម្លៃ — បង្ហាញជា **ការជំរុញ** (BR10)

ពេលអ្នកប្រើកែចំនួន សូមបង្ហាញភ្លាមៗ៖

| ចំនួននាក់ | បញ្ចុះ | សារជំរុញលើអេក្រង់ |
|---|---|---|
| ១–២ | ០% | *"បន្ថែម ១ នាក់ទៀត ទទួលបញ្ចុះ ៥%!"* |
| ៣–៤ | ៥% | *"បន្ថែម ១ នាក់ទៀត ទទួលបញ្ចុះ ១០%!"* |
| ៥–៩ | ១០% | *"ដល់ ១០ នាក់ ទទួលបញ្ចុះ ១៥%!"* |
| ១០+ | ១៥% | *"អ្នកទទួលបានបញ្ចុះក្រុមធំ ១៥%"* |

### ៤.៣ វិន័យដែលត្រូវពិនិត្យ **នៅ Frontend មុន**

**កុំបង្ខំ**៖ មានតែ `rating` ទេដែលចាំបាច់។ បើបង្ខំបំពេញទាំង ៣ អត្រាបំពេញនឹងធ្លាក់ខ្លាំង។

### ៧.៤ ផលប៉ះពាល់ក្រោយវាយតម្លៃ

```
Review បង្កើត ─> recalculateRating(tourId)
                    ↓
        tour.averageRating · tour.reviewCount ប្តូរ
                    ↓
        TourCardResponse លើទំព័រដើមប្តូរតាម
```

### ៧.៥ ផ្នែក Admin លើវាយតម្លៃ

| សកម្មភាព | ឥទ្ធិពលលើអ្នកប្រើ |
|---|---|
| `POST /reviews/{id}/reply` | ចម្លើយបង្ហាញក្រោមមតិ ជាមួយស្លាក "ការឆ្លើយតបពីអ្នកគ្រប់គ្រង" — បង្កើនទំនុកចិត្តខ្លាំង |
| `PATCH /reviews/{id}/hide` | `isVisible = false` → បាត់ពីសាធារណៈ **តែម្ចាស់នៅឃើញ** ព្រមទាំង `hiddenReason` |

> ⚠️ ការលាក់មិនគួរប៉ះពាល់ `averageRating` ទេ បើមិនដូច្នេះ Admin អាចលាក់មតិអវិជ្ជមានដើម្បីលើកពិន្ទុ។ `recalculateRating` បច្ចុប្បន្ន **មិនត្រង `isVisible`** ទេ — នេះជាការសម្រេចចិត្តត្រឹមត្រូវ សូមរក្សាទុក។

## ៨. ដំណើរផ្នែក Admin (Back Office)

### ៨.១ ផ្ទាំងការងារប្រចាំថ្ងៃ

```
┌─ ត្រូវធ្វើថ្ងៃនេះ ────────────────────┐
│ ⏳ ការទូទាត់រង់ចាំផ្ទៀងផ្ទាត់     ៧    │ ← UC8.3 អាទិភាពខ្ពស់
│ ⏳ ការកក់រង់ចាំបញ្ជាក់           ១២   │ ← UC7.5
│ 📅 កាលវិភាគគ្មានមគ្គុទ្ទេសក៍      ៣    │ ← UC5.x
│ 💬 វាយតម្លៃថ្មីមិនទាន់ឆ្លើយ      ៥    │ ← UC9.5
└───────────────────────────────────────┘
```

### ៨.២ លំដាប់ការងារ "ផ្ទៀងផ្ទាត់ការទូទាត់"

```
១. បើកបញ្ជីការទូទាត់ status = PENDING
        ↓
២. ចុចមួយ → បង្ហាញ receiptUrl ធំៗ ក្បែរចំនួនទឹកប្រាក់
        ↓
៣. ប្រៀបធៀបជាមួយ statement ធនាគារ
        ↓
   ┌────┴────┐
[បញ្ជាក់]  [បដិសេធ + មូលហេតុ]
   │           │
VERIFIED    REJECTED
   │           │
syncBookingPaidAmount()   ជូនដំណឹងអតិថិជន
   │
បង់គ្រប់? → CONFIRMED ស្វ័យប្រវត្តិ
```

**UX សំខាន់**៖ ដាក់ **រូបវិក្កយបត្រ និងចំនួនទឹកប្រាក់ក្នុងអេក្រង់តែមួយ** — Admin មិនគួរត្រូវបើកផ្ទាំងថ្មីដើម្បីមើលរូបទេ ព្រោះគាត់ធ្វើការនេះ ៥០ ដងក្នុងមួយថ្ងៃ។

### ៨.៣ ចាត់តាំងមគ្គុទ្ទេសក៍ (F5 + F3)

```
PATCH /api/v1/schedules/{id}/guide
```

Repository មាន `hasGuideConflict(guideId, start, end, excludeScheduleId)` — មានន័យថា **បញ្ជីជម្រើសមគ្គុទ្ទេសក៍ត្រូវច្រោះរួចជាស្រេច**៖

```
ជ្រើសមគ្គុទ្ទេសក៍សម្រាប់ ១២–១៤ តុលា:
  ● សុខ ដារ៉ា      ✅ ទំនេរ
  ● ចាន់ សុភា      ✅ ទំនេរ
  ○ លី វិចិត្រ      ⛔ ជាប់ដំណើរ ១០–១៥ តុលា    ← បិទមិនឲ្យជ្រើស
  ○ ម៉ៅ សំណាង      ⛔ ស្ថានភាព: ON_LEAVE
```

មិនមែនទុកឲ្យជ្រើសរួចបោះកំហុស 409 ទេ។

| Job | ពេលរត់ | អ្នកប្រើឃើញអ្វី |

## ១១. សរុប — ៥ គោលការណ៍ UX ចម្បង

1. **វិន័យណា UI ការពារបាន ត្រូវការពារនៅ UI** — `minGroupSize`, `availableSeats`, `isLead`, ចំនួន passenger
2. **បង្ហាញលទ្ធផលមុនសកម្មភាព** — តារាងសងប្រាក់មុនលុបចោល · បញ្ចុះតម្លៃមុនកក់
3. **បែងចែក "រង់ចាំ" និង "បញ្ជាក់រួច" ឲ្យច្បាស់** — ជាពិសេសផ្នែកទឹកប្រាក់
4. **ឆ្លុះបញ្ចាំង job ស្វ័យប្រវត្តិលើអេក្រង់** — នាឡិកា ២៤ ម៉ោង · ការអញ្ជើញវាយតម្លៃ
5. **លាក់ប៊ូតុងដែលនឹងបរាជ័យ** — ជំនួសឲ្យបង្ហាញរួចបោះ 409/422
